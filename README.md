# Архитектурное проектирование системы маркетплейса

## Описание проекта

Цифровая платформа, на которой продавцы размещают товары, а пользователи оформляют заказы. Система реализует персонализированную выдачу товаров, управление каталогом, обработку заказов и платежей, а также отправку уведомлений.

---

## Архитектура системы (C4 Container Diagram)

См. файл `diagrams/C4-container.png`

### Описание компонентов

| Компонент | Технология | Назначение |
|-----------|-----------|-----------|
| Web Application | React SPA | Клиентский интерфейс для покупателей и продавцов |
| API Gateway | Nginx/Kong | Маршрутизация, аутентификация, rate limiting |
| User Service | FastAPI + PostgreSQL | Управление пользователями и аутентификация |
| Catalog Service | FastAPI + PostgreSQL | Управление товарами и категориями |
| Order Service | FastAPI + PostgreSQL | Оформление и управление заказами |
| Payment Service | FastAPI + PostgreSQL | Обработка платежей и транзакций |
| Notification Service | FastAPI + Redis | Отправка уведомлений о статусах |
| Recommendation Service | FastAPI + PostgreSQL | Персонализированные рекомендации |
| RabbitMQ | RabbitMQ | Асинхронное взаимодействие сервисов |

## Доменная модель

Система разделена на 6 доменов по принципу Bounded Context (DDD):

### 1. User Domain
**Ответственность:** Управление пользователями платформы
- Регистрация и аутентификация
- Управление профилями (покупатели и продавцы)
- Роли и права доступа

### 2. Catalog Domain
**Ответственность:** Управление товарным каталогом
- CRUD операции с товарами
- Категории и атрибуты товаров
- Управление ценами и остатками
- Модерация товаров

### 3. Order Domain
**Ответственность:** Оформление и жизненный цикл заказов
- Создание заказов из корзины
- Управление статусами заказа
- История заказов пользователя
- Возвраты и отмены

### 4. Payment Domain
**Ответственность:** Финансовые операции
- Обработка платежей
- Транзакции и чеки
- Возвраты средств
- Интеграция с платёжными системами

### 5. Notification Domain
**Ответственность:** Коммуникация с пользователями
- Email-уведомления
- Push-уведомления
- Уведомления о статусах заказов
- Маркетинговые рассылки

### 6. Recommendation Domain
**Ответственность:** Персонализация пользовательского опыта
- Анализ поведения пользователей
- Формирование персональной ленты товаров
- ML-модели рекомендаций
- A/B тестирование алгоритмов

## Распределение доменов по сервисам

| Сервис | Домен | Обоснование размещения |
|--------|-------|----------------------|
| User Service | User Domain | Прямое соответствие: сервис управляет сущностями домена |
| Catalog Service | Catalog Domain | Прямое соответствие: сервис управляет каталогом |
| Order Service | Order Domain | Прямое соответствие: сервис управляет заказами |
| Payment Service | Payment Domain | Выделен в отдельный сервис из-за строгих требований к надёжности и аудиту финансовых операций |
| Notification Service | Notification Domain | Выделен как асинхронный сервис, не блокирующий основные бизнес-процессы |
| Recommendation Service | Recommendation Domain | Выделен из-за необходимости использования специализированных ML-инструментов и векторных БД |

**Логика разбиения:**
1. **Single Responsibility** — каждый сервис отвечает за один домен
2. **Разная частота изменений** — каталог меняется чаще платежей
3. **Разные технологические требования** — рекомендации требуют ML-стека
4. **Независимое масштабирование** — каталог читается чаще, чем оформляются заказы

## Границы владения данными

### Принцип Database per Service

Каждый сервис владеет исключительно своими данными. Разделяемые базы данных между сервисами **отсутствуют**.

| Сервис | Владеет данными | Отвечает за |
|--------|----------------|-------------|
| User Service | Пользователи, профили, токены | Чтение/запись пользовательских данных |
| Catalog Service | Товары, категории, атрибуты | Актуальность каталога, поиск товаров |
| Order Service | Заказы, позиции заказа, статусы | Жизненный цикл заказа |
| Payment Service | Платежи, транзакции, чеки | Финансовая целостность операций |
| Notification Service | Шаблоны уведомлений, история отправок | Доставка уведомлений пользователям |
| Recommendation Service | Пользовательские предпочтения, модели | Качество рекомендаций |

### Взаимодействие через данные

Сервисы **не имеют прямого доступа** к БД друг друга. Данные передаются двумя способами:

1. **Синхронно (REST API)** — когда нужен немедленный ответ
   - Order Service → User Service: получить данные пользователя для заказа
   - Order Service → Catalog Service: проверить наличие товара

2. **Асинхронно (Message Broker)** — когда можно обработать позже
   - Order Service → Notification Service: уведомить о статусе заказа
   - Catalog Service → Recommendation Service: обновить данные для рекомендаций

## Альтернативные варианты декомпозиции

### Вариант 1: Мелкозернистые микросервисы (выбранный)

6 независимых сервисов, каждый отвечает за один домен.

**Плюсы:**
- Максимальная независимость команд и развёртывания
- Оптимальный выбор технологий для каждого домена
- Изоляция отказов (падение одного сервиса не влияет на другие)
- Независимое масштабирование компонентов

**Минусы:**
- Высокая сложность инфраструктуры (оркестрация, мониторинг)
- Распределённые транзакции требуют Saga pattern
- Сетевые задержки между сервисами
- Сложность отладки распределённой системы

### Вариант 2: Модульный монолит

Единое приложение с чётко разделёнными модулями по доменам.

**Плюсы:**
- Простота разработки и развёртывания
- Нет сетевых задержек между модулями
- Простые ACID-транзакции
- Единая кодовая база, проще рефакторинг

**Минусы:**
- Ограниченная масштабируемость (только вертикальная)
- Риск создания "big ball of mud" при росте
- Сложность работы больших команд (конфликты в коде)
- Падение одного модуля = падение всей системы

### Вариант 3: Среднезернистые сервисы (объединённые домены)

3 сервиса вместо 6:
- **User & Notification Service** — пользователи + уведомления
- **Catalog & Recommendation Service** — каталог + рекомендации
- **Order & Payment Service** — заказы + платежи

**Плюсы:**
- Баланс между независимостью и сложностью управления
- Меньше сетевых вызовов между связанными доменами
- Проще управлять транзакциями внутри объединённого домена
- Меньше инфраструктурных затрат

**Минусы:**
- Менее гибкое масштабирование (нельзя масштабировать только платежи)
- Риск нарушения Single Responsibility
- Сложнее разделить команды в будущем
- Зависимость между доменами внутри сервиса

## Обоснование финального выбора

**Выбран Вариант 1: Мелкозернистые микросервисы**

### Аргументация

1. **Требования кейса о персонализации**  
   Recommendation Domain требует специализированного стека (ML-модели, векторные БД). Выделение в отдельный сервис позволяет использовать оптимальные инструменты без влияния на другие компоненты.

2. **Разная нагрузка на компоненты**  
   Каталог читается значительно чаще, чем оформляются заказы. Независимое масштабирование Catalog Service критично для производительности.

3. **Требования к надёжности платежей**  
   Payment Domain имеет строгие требования к аудиту и отказоустойчивости. Изоляция в отдельном сервисе позволяет применить специализированные паттерны (Saga, idempotency) без усложнения других сервисов.

4. **Асинхронная природа уведомлений**  
   Notification Service по своей природе асинхронный. Выделение в отдельный сервис предотвращает блокировку основных бизнес-процессов при проблемах с доставкой уведомлений.

5. **Перспектива роста команды**  
   Архитектура позволяет распределить работу между 6 независимыми командами без конфликтов и блокировок.

6. **Соответствие принципам СОА**  
   - Слабая связность (loose coupling) через Message Broker
   - Высокая связность внутри сервиса (high cohesion)
   - Независимое развёртывание каждого сервиса
   - Владение данными (database per service)

## Инструкция по запуску

### Предварительные требования

- Docker и Docker Compose установлены на машине
- Python 3.11+ (опционально, для локального запуска без Docker)

### Запуск через Docker Compose

1. Клонируйте репозиторий:
```bash
git clone <repository-url> # можно найти через кнопку "Code"
cd SOA_project
```

2. Запустите сервис:
```bash
docker-compose up --build
```

3. Проверьте health-check endpoint:
```bash
curl http://localhost:8000/health
```

Ожидаемый ответ:
```json
{"status": "ok"}
```

4. Остановите сервис:
```bash
docker-compose down
```

### Локальный запуск (без Docker)

1. Установите зависимости:
```bash
pip install -r requirements.txt
```

2. Запустите сервис:
```bash
uvicorn main:app --host 0.0.0.0 --port 8000
```

3. Проверьте health-check:
```bash
curl http://localhost:8000/health
```

### Проверка через браузер

Откройте в браузере: http://localhost:8000/health

Должна отобразиться JSON-страница: `{"status": "ok"}`
